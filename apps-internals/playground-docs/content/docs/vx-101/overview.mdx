# Vezham — GitHub, Repository & Package Organization

## 1. GitHub Organizations

Vezham uses exactly **three GitHub organizations**.

| Organization  | Purpose                                                     | Description                                                |
| ------------- | ----------------------------------------------------------- | ---------------------------------------------------------- |
| `vezham`      | Production engineering, products, platforms, infrastructure | **Building software for people and businesses. 🚀**        |
| `vezham-labs` | Experiments, templates, POCs, references, evolving tooling  | **Exploring ideas, experiments, and new technologies. 🧪** |
| `vezham-oss`  | Open-source projects and maintained forks                   | **Open-source software maintained by Vezham. 🧩**          |

### Classification rule

- `vezham` → official production Vezham engineering
- `vezham-labs` → experimental/evolving/reference projects
- `vezham-oss` → maintained OSS projects and forks
- An OSS fork remains under `vezham-oss` even when used in production.
- A completely new Vezham implementation/rewrite can live under `vezham`.

# 23. Environment Architecture

Vezham uses five primary deployment environments:

```text
local → dev → qa → preview → production
```

| Environment  | Purpose                                                                                   |
| ------------ | ----------------------------------------------------------------------------------------- |
| `local`      | Developer machine and local development                                                   |
| `dev`        | Active development                                                                        |
| `qa`         | Integration and QA validation                                                             |
| `preview`    | Production-like validation, security auditing, realistic/snapshot data, and V1/V2 testing |
| `production` | Live production infrastructure                                                            |

### Environment URLs

```text
play.vezham.local
play.dev.vezham.com
play.qa.vezham.com
play.preview.vezham.com
play.vezham.app
```

The engineering/pre-production environments use `vezham.com`.

Production user-facing applications use `vezham.app`.

# 24. Preview Environment

`preview` is intentionally a real deployment environment.

It is used for:

- production-like validation
- realistic/snapshot data
- V1/V2 comparison
- UI validation
- integration validation
- security audits
- pre-production security verification
- production configuration validation
- release candidate verification

Preview should normally use **production-like data**, not unrestricted direct read/write access to the live production database.

Preferred model:

```text
Production DB
      │
      ├── sanitized snapshot
      │
      ├── replica
      │
      └── controlled read-only access
                ↓
             Preview
```

The exact mechanism depends on the data/security requirements of the application.

# 25. Release Channels

Release channels are separate from deployment environments.

```text
canary → beta → stable
```

| Channel  | Purpose                         |
| -------- | ------------------------------- |
| `canary` | Very limited production rollout |
| `beta`   | Controlled early-access rollout |
| `stable` | General production release      |

The release channel can be controlled through configuration and feature flags.

Example:

```text
V_APP_ENV=production
V_RELEASE_CHANNEL=beta
```

Later:

```text
V_APP_ENV=production
V_RELEASE_CHANNEL=stable
```

This means Beta does not require a separate infrastructure environment.

`@vx/env/vite` and `@vx/env/next` expose these settings as `APP_ENV` and
`RELEASE_CHANNEL`. Omit `V_APP_ENV` for local development and set `V_APP_ENV=dev`
for deployed development infrastructure. Build mode remains independent:
`__DEV__` and `__PRODUCTION__` describe the build, while `APP_ENV` describes the
deployment. Set `V_APP_ENV=qa` or `V_APP_ENV=preview` explicitly for those
deployments. Absent or empty `V_APP_ENV` defaults to `local`, including for local
production builds. Checked-in app configs omit it; deployment pipelines must
supply and validate their target environment. `V_APP_ID`, `V_APP_NAME`, and `V_APP_VER` are required
and supplied from `vx.app.yaml` by metadata generation. `V_RELEASE_CHANNEL` is
the only release-channel input and defaults to `stable`.

# 26. Environment vs Release Channel

The core rule is:

> **Environment describes where/how software runs. Release channel describes which release users receive.**

Therefore:

```text
Environments
local
dev
qa
preview
production
```

and:

```text
Release channels
canary
beta
stable
```

can evolve independently.

Conceptually:

```text
                         ┌── canary
production ──────────────┼── beta
                         └── stable
```

Preview remains a separate pre-production validation environment.

# 27. Build Once, Promote the Same Artifact

The deployment architecture follows an immutable-artifact model.

When `timeline` receives a merge:

```text
feature branch
      ↓
     PR
      ↓
  timeline
      ↓
    build
      ↓
immutable artifact
```

Example:

```text
Application: play
Version:     1.8.0
Commit:      a81f92c
Artifact:    play-1.8.0-a81f92c
```

The same artifact is promoted through:

```text
dev → qa → preview → production
```

Do **not** rebuild the application separately for each environment.

The artifact remains immutable while environment configuration changes.

# 29. Deployment Workflows

Initial workflow structure:

```text
.github/workflows/
├── build.yml
├── deploy.yml
├── promote.yml
└── rollback.yml
```

## `build.yml`

Triggered by merge/push to `timeline`.

Responsibilities:

```text
checkout
   ↓
test
   ↓
lint/typecheck
   ↓
build
   ↓
create immutable artifact
   ↓
publish artifact
```

Example artifact identity:

```text
play-1.8.0-a81f92c
```

## `deploy.yml`

Deploys an artifact to a selected environment.

Conceptually:

```yaml
jobs:
  deploy:
    environment:
      name: preview
      url: https://play.preview.vezham.com
```

GitHub then records:

```text
environment
commit
workflow
actor
deployment status
deployment time
URL
```

## `promote.yml`

Promotes an existing artifact between environments.

Example:

```text
Artifact:
play-1.8.0-a81f92c

From:
qa

To:
preview
```

The workflow:

```text
download exact artifact
        ↓
validate promotion
        ↓
deploy target environment
        ↓
record deployment
```

No rebuild occurs.

## `rollback.yml`

Rolls back to a previously deployed artifact.

Example:

```text
production
v1.8.0
   ↓
rollback
   ↓
v1.7.4
```

The previous artifact is redeployed rather than rebuilt.

# 31. Production Release Channels

Production deployment and production exposure are separate operations.

After an artifact reaches production:

```text

     │
     ├── canary
     ├── beta
     └── stable
```

Example:

```text
Production
│
├── Canary → 1%
├── Beta   → 10%
└── Stable → 89%
```

Or release channels can be user/organization based:

```text
Canary → internal users
Beta   → opted-in users

```

The exact rollout mechanism can use:

- traffic splitting
- feature flags
- user targeting
- workspace targeting

# 34. Rollback Model

Rollback must use an existing immutable artifact.

Example:

```text
production
v2.1.0

error detected
   ↓
rollback
   ↓
v2.0.4
```

No rebuild should occur.

The failed artifact remains available for investigation.

# 37. Core Architecture Principles

### 1. Application = Product Boundary

A repository should primarily represent an application/domain/product responsibility.

### 2. Workspace = Data/Access Boundary

A workspace determines:

- ownership
- membership
- permissions
- context
- storage
- synchronization
- organization relationship

### 3. Environment ≠ Release Channel

```text
Environment → where/how it runs
Channel     → who receives the release
```

### 4. Build Once, Promote Many

```text
Source
  ↓
Build once
  ↓
Immutable artifact
  ↓
dev → qa → preview → production
```

### 5. Production-like Testing Before Production

`preview` exists specifically so Vezham can validate releases against realistic conditions, including **security auditing**, before production exposure.

### 6. Canary/Beta Do Not Require Separate Infrastructure

They can be implemented through:

- release configuration
- feature flags
- user targeting
- organization targeting
- traffic allocation
- progressive rollout

### 7. GitHub Handles the Initial Deployment Ledger

Use GitHub's native:

- Actions
- Environments
- Deployments
- Artifacts
- Secrets
- Variables
- Protection rules

before building a custom deployment database.

### 8. `vx-deployer` Owns Promotion and Release Orchestration

Git branches determine source history.

`vx-deployer` determines:

```text
where an artifact runs
when it is promoted
which release is exposed
how it is rolled back
```

### 9. Own Abstractions Only When Necessary

Use:

```text
upstream → when appropriate
@vx-oss/* → maintained OSS fork
@vezham/* → strategic Vezham abstraction
```

### 10. Official Infrastructure Belongs in `vezham`

Production deployment infrastructure belongs under:

```text
vezham
```

while experiments and evolving tooling belong under:

```text
vezham-labs
```

### 11. OSS Forks Stay OSS

A maintained OSS fork remains under:

```text
vezham-oss
```

even when Vezham consumes it internally or in production.
