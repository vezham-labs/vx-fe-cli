# 1. Engineering Model

Vezham follows a domain-oriented engineering architecture across three GitHub organizations:

```text
                         VEZHAM
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
       vezham          vezham-labs       vezham-oss
          │                 │                 │
      Production         Research          OSS/Forks
      Engineering        Experiments
          │
   ┌──────┼─────────────────────────────────────────┐
   │      │             │          │                │
  FE     RN           BE         SDKs          Docs / AI
   │      │             │          │                │
 Apps   Apps         Services   Language      Docs / MCP / Skills
 Packages             APIs       SDKs
   │
   ├── General Apps
   └── Business Apps
```

### Core principles

1. **Application = Product Boundary**
2. **Workspace = Data / Access Boundary**
3. **Environment ≠ Release Channel**
4. **Build Once, Promote Many**
5. **Production-like Testing Before Production**
6. **Canary/Beta Do Not Require Separate Infrastructure**
7. **GitHub Handles the Initial Deployment Ledger**
8. **`vx-deployer` Owns Promotion and Release Orchestration**
9. **Own Abstractions Only When Necessary**
10. **Official Infrastructure Belongs in `vezham`**
11. **OSS Forks Stay in `vezham-oss`**
12. **Every Build Has an Immutable Commit-SHA Identity**
13. **TVA Represents the Individual Timeline Variant of a Commit**

# 21. TVA — Time Variance Authority

Vezham introduces a commit-specific deployment layer called **TVA — Time Variance Authority**.

The name intentionally aligns with the `timeline` branch and Marvel's TVA concept.

TVA represents an individual **timeline variant of a specific commit**.

Every build can receive a commit-SHA-specific URL.

Example:

```text
play.a81f92c.tva.vezham.com
```

This URL represents:

```text
Application: play
Commit:      a81f92c
Variant:     TVA
```

Multiple commit variants can coexist:

```text
play.a81f92c.tva.vezham.com
play.b72c441.tva.vezham.com
play.c91de20.tva.vezham.com
```

TVA is **not another promotion environment**.

It is the immutable, commit-specific validation identity of an artifact.

---

# 22. SHA Preview URL

Recommended format:

```text
<app>.<commit-sha>.tva.vezham.com
```

Example:

```text
play.a81f92c.tva.vezham.com
```

The SHA URL is generated when the build is created.

It provides:

- exact commit identification
- immutable validation
- PR review URL
- visual/UI testing
- integration testing
- debugging
- stakeholder review
- reproducibility

A GitHub PR can therefore expose:

```text
PR #142
Commit: a81f92c

TVA:
https://play.a81f92c.tva.vezham.com
```

# 23. Build Once, Promote the Same Artifact

This is a fundamental Vezham deployment principle:

> **Build once, promote the same artifact.**

Example:

```text
Application: play
Version:     1.8.0
Commit:      a81f92c
Artifact:    play-1.8.0-a81f92c
```

Build:

```text
timeline
    ↓
build
    ↓
immutable artifact
    ↓
TVA
    ↓
play.a81f92c.tva.vezham.com
```

The artifact is then promoted without rebuilding:

```text
TVA
 ↓
DEV
 ↓
QA
 ↓
PREVIEW
 ↓
PRODUCTION
```

The artifact must remain immutable throughout this process.

# 24. Promotion URLs

Stable environment URLs represent the currently promoted artifact.

```text
play.dev.vezham.com
play.qa.vezham.com
play.preview.vezham.com
play.vezham.app
```

Therefore:

```text
play.a81f92c.tva.vezham.com
          │
          │ promote
          ▼
play.dev.vezham.com
          │
          │ promote
          ▼
play.qa.vezham.com
          │
          │ promote
          ▼
play.preview.vezham.com
          │
          │ promote
          ▼
play.vezham.app
```

The stable environment URL changes which artifact it points to.

The TVA URL remains tied to the original commit/artifact.

---

# 25. Environment vs TVA

The distinction is:

```text
TVA
└── Which exact commit/artifact?

Environment
└── Where is that artifact currently promoted?
```

Therefore:

```text
play.a81f92c.tva.vezham.com
```

means:

> Run exactly commit `a81f92c`.

Whereas:

```text
play.qa.vezham.com
```

means:

> Run the artifact currently promoted to QA.

# 26. Release Channels

Production has release channels:

```text
canary → beta → stable
```

| Channel  | Purpose                         |
| -------- | ------------------------------- |
| `canary` | Very limited production rollout |
| `beta`   | Controlled early-access rollout |
| `stable` | General production release      |

Channels are not separate environments.

Example:

```text
APP_ENV=production
RELEASE_CHANNEL=beta
```

Then:

```text
APP_ENV=production
RELEASE_CHANNEL=stable
```

Production can therefore contain:

```text
production
    │
    ├── canary
    ├── beta
    └── stable
```

Release targeting may use:

- traffic splitting
- feature flags
- user targeting
- workspace targeting
- organization targeting
- region targeting

# 28. GitHub Commit Deployment Status

Each commit acts as a visible timeline record.

For example:

```text
Commit: a81f92c

Deployment Status

TVA       ✓ deployed
DEV       ✓ promoted
QA        ✓ promoted
PREVIEW   ⏳ pending
PROD      —
```

Each successful promotion can expose:

```text
Environment: QA
Artifact:    play-1.8.0-a81f92c
Commit:      a81f92c
From:        DEV
To:          QA
Status:      SUCCESS
```

The commit's GitHub Checks/Deployments provide the authoritative deployment state.

A human-readable commit comment can additionally summarize the promotion history.

### Important rule

The commit comment is **not the source of truth**.

The authoritative state is:

```text
GitHub Deployments / Checks
        ↓
vx-deployer
        ↓
Deployment state
```

The comment is a convenient human-readable timeline.

# 29. GitHub Actions

Initial workflow structure:

```text
.github/workflows/
├── build.yml
├── deploy.yml
├── promote.yml
└── rollback.yml
```

## `build.yml`

Triggered by merge/push to `timeline`.

Responsibilities:

- install dependencies
- lint
- typecheck
- test
- build
- create immutable artifact
- publish artifact
- generate TVA deployment
- expose TVA URL
- update GitHub commit status

Example:

```text
timeline
   ↓
build.yml
   ↓
play-1.8.0-a81f92c
   ↓
play.a81f92c.tva.vezham.com
```

## `deploy.yml`

Deploys a selected artifact to a selected environment.

GitHub Environment example:

```yaml
jobs:
  deploy:
    environment:
      name: preview
      url: https://play.preview.vezham.com
```

GitHub records:

- environment
- commit
- workflow
- actor
- deployment status
- time
- URL

## `promote.yml`

Promotes an existing artifact.

Example:

```text
Artifact: play-1.8.0-a81f92c
From:     QA
To:       Preview
```

No rebuild occurs.

## `rollback.yml`

Redeploys an existing immutable artifact.

Example:

```text
production
v2.1.0
   ↓
problem
   ↓
rollback
   ↓
v2.0.4
```

No rebuild occurs.

GitHub provides the visible deployment/check history.

`vx-deployer` controls promotion and release orchestration.

The commit SHA remains the identity of the artifact throughout its lifecycle.

# 43. Canonical Principles

### 1. Application = Product Boundary

Applications define product ownership and repository boundaries.

### 2. Workspace = Data / Access Boundary

Workspace determines context, access and data isolation.

### 3. Environment ≠ Release Channel

Environment determines **where/how** software runs.

Channel determines **which release users receive**.

### 4. Build Once, Promote Many

Never rebuild an artifact merely because it moves environments.

### 5. TVA = Timeline Variant

Every build can have an immutable commit-SHA URL.

```text
<app>.<sha>.tva.vezham.com
```

### 6. GitHub Is the Initial Deployment Ledger

GitHub Deployments, Checks, Actions, Environments and Artifacts provide the initial source of deployment history.

### 7. Commit Comments Are Human-Friendly History

Commit comments can display promotion status, but GitHub Deployments/Checks remain authoritative.

### 8. Preview Before Production

Production-like validation happens before production promotion.

### 9. Canary/Beta/Stable Are Release Channels

They do not require separate environments.

### 10. Rollback Means Re-Promotion

Rollback uses an existing immutable artifact.

### 11. OSS Forks Stay OSS

Maintained forks remain under `vezham-oss`.

### 12. Official Infrastructure Belongs in `vezham`

Production engineering infrastructure does not live in Labs.
